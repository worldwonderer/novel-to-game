# 测试设计方法

用最少证据证明当前 profile 声明的玩家体验。

## 一、从 profile 建立范围

先列当前 profile 的 required set，再加入项目实际采用的语音、多语言、无障碍、媒体或连续 3D
检查。每项检查对应一个玩家可感知结果和一份可复核证据。

## 二、三类证据

- **确定性证据**：状态迁移、关键事实写入与读取、规则、门槛、结果、存档和重开；
- **观察性证据**：真实画面、输入、转场、可读性、声音、目标显示与设备表现；
- **试玩观察**：人物理解、选择重量、节奏、情绪、上手、策略和手感。

三类证据分别回答实现是否成立、玩家是否看到，以及玩家如何理解和感受。

确定性证据可以证明路径可达、事实按顺序写入和读取、人物没有使用未获得信息、逐字文案出现正确
变体以及重开清空状态；它不能证明台词自然、人物有魅力、选择有重量、节奏合适或玩家沉浸。

## 三、按体验档案设计断言

从 GAME_DESIGN 选择当前项目已经承诺的体验因果：

- 场景和人物：人物目标、知识状态、时间地点、物件与连续性；
- 关键选择：玩家输入写入具体事实，后续场景、人物、对白、信息或结局读取；
- 动作和规则：输入、反馈、状态变化、规则读取、推进、结果和恢复；
- 剧情与系统连接：记录连接前状态、玩家输入、连接后状态和玩家可见反馈；
- 双向连接：分别覆盖剧情事实影响系统条件、系统结果影响后续剧情。

代表节点和局面来自 CONCEPT 与 GAME_DESIGN。固定种子用于可复现规则。

每项关键分支至少设计一条正向路径和一条反向路径：正向证明已选择事实被消费，反向路径证明未选
事实不会串入人物知识、对白、案卷、场景或结果。汇流点同时检查共享内容与历史变体。

## 四、完整路径

从 clean start 走到设计结果再 restart。checkpoint 保留：触发输入、预期变化、状态证据、运行环境
证据和必要代表帧。语义发生变化时建立 checkpoint，使整条路径保持紧凑。

时序、动效、碰撞和连续镜头在正常速度下采集。状态、runtime 与画面共同描述同一次运行。

## 五、首次上手与独立试玩

`delivery` 记录未读策划玩家的第一场景体验：他如何描述身份、处境、第一次参与和当前目标。
`release` 记录目标玩家独立完成主要路径的过程、原话和问题。

试玩问题跟随体验档案，可覆盖人物、信息、选择、回响、上手、判断、反馈、手感和两层连接的理解。

文案自然度、人物声音、沉浸、选择重量和主观节奏需要独立审查或目标玩家证据。构建者、作者或当前
设计所有者自检只能记录为 `provisional` 发现，不能代替独立审查，也不能把自己的接受意见签成
最终 PASS。

## 六、证据与报告

证据使用工作区相对路径并保持可复跑。保存当前结论真正引用的状态记录、代表帧、短录制和试玩
记录。

每个 limitation 记录 scope、reason 与 blocksProfiles。`QA_REPORT.md` 汇总环境、命令、完整路径、
结果、问题归属、试玩观察和未覆盖范围。

报告把“已由自动化证明”“已由独立证据支持”“所有者自检发现”与“尚未验证”分开，不用结构字段
齐全、测试退出码或一次顺利走通冒充体验质量结论。
